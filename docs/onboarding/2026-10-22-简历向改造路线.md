## 三、三个短板：只学最小集，然后落地到项目里

学习原则：**不要先系统学一遍再动手**。每个短板挑 5 个概念 + 1 个代码改造 + 1 个可量化产出，三天就能从"不深"到"能答 3 层"。

### 3.1 向量数据库（建议 3~4 天，性价比最高）

**只学这 5 个概念**：

| 概念 | 你必须能答的那句话 |
|---|---|
| Flat / IVF / HNSW | Flat 精确但 O(n)，IVF 靠聚类剪枝，HNSW 靠多层跳表近似，召回与内存换速度 |
| cosine vs L2 | 文本 embedding 通常已归一化，两者等价；未归一化时 cosine 更稳 |
| `M` / `efSearch` | M 控制图连通度（内存↑ 召回↑），efSearch 控制查询时搜索宽度（延迟↑ 召回↑） |
| 增量写入 | FAISS 的 `add_documents` 是追加，删除要靠 `remove_ids` 或重建 |
| 召回评估 | Recall@k 是"该找到的有没有找到"，与生成质量解耦 |

**项目里的改造**（`src/retrieval/vector_search.py`）：

1. 加 HNSW 索引：`faiss.IndexHNSWFlat(dim, M=32)`，设置 `hnsw.efSearch`。
2. 加元数据过滤：检索时按 `source_type` 过滤（法律问题优先召回法条，其次案例）。
3. 索引落盘带版本号：`index_path/v1_<语料条数>/`，避免语料变了索引没变。
4. 加增量入口：新法条导入时 `add_documents` 而不是全量重建。

**产出**（这张表就是 Bullet 3 的数字来源）：

| 索引 | 语料 100 条 | 1000 条 | 10000 条 |
|---|---|---|---|
| Flat | Recall / 延迟 | | |
| HNSW(M=32) | | | |

**面试三问**：
- 为什么用 FAISS 不用 Milvus / pgvector？→ 单机、无服务依赖、数据量 < 10 万时够用；Milvus 适合分布式，pgvector 适合已有 PG 且要事务一致性。
- HNSW 召回不够怎么调？→ 先调 efSearch（延迟换召回），再调 M（内存换召回），最后考虑换 IVF-PQ。
- 索引和数据库不一致怎么办？→ 版本号 + 语料指纹，启动时校验。

### 3.2 GraphRAG（建议 5~6 天，最能体现差异）

**只学这 5 个概念**：

| 概念 | 你必须能答的那句话 |
|---|---|
| KG schema | 节点类型 = 你要回答的问题类型（法条、案例、争议焦点），边 = 推理路径 |
| 实体关系抽取 | LLM 按 JSON schema 抽取 + 人工校验，不要指望一次抽全 |
| 多跳 | 1 跳找直接依据，2 跳找"同类案例还引用了什么"，3 跳开始噪声大于收益 |
| 图-向量融合 | 图给结构化约束和可解释路径，向量给语义泛化，融合解决"各漏一半" |
| 何时图更强 | 有明确实体（条号、罪名）时图强；口语化描述、同义改写时向量强 |

**项目里的改造**：

1. **schema 升级**（`kg_builder.py`）：从 2 类节点扩到 4 类 —— `Law`（法）、`Article`（条）、`Case`（案）、`Issue`（争议焦点）；边从 1 种扩到 4 种 —— `APPLIES`（案→条）、`BELONGS_TO`（条→法）、`INTERPRETS`（案→焦点）、`CITES`（案→案）。
2. **抽取流水线**：`collector → processor → LLM 结构化抽取 → 人工抽检 20 条 → 入库`，抽检准确率写进 README。
3. **查询双路保底**：模板 Cypher（确定性高、覆盖 80% 场景）+ Text2Cypher（LLM 生成，失败回退模板）。**别只做 Text2Cypher**，LLM 生成的 Cypher 语法错误率很高。
4. **消融实验**：同一 gold set 跑三组（vector / graph / hybrid），出 Recall@5 + MRR 对比表。

**产出**：图谱规模（节点数 / 边数 / 抽取准确率）+ 三组消融数字 + 一张"图检索救回了向量漏掉的哪几条"的案例。

**面试三问**：
- GraphRAG 比普通 RAG 强在哪？→ 结构化约束（条号精确匹配）+ 可解释路径（为什么这条法条相关）+ 多跳发现（同类案例的关联法条）。
- 构建图谱成本多少？→ 抽取 token 数 / 人工校验工时，诚实说"千条级 corpus 才划算"。
- 二跳为什么不是三跳？→ 噪声与延迟的权衡，用实验说话。

### 3.3 多智能体（建议 3~4 天，最容易讲成故事）

**只学这 5 个概念**：

| 概念 | 你必须能答的那句话 |
|---|---|
| 编排 vs 协作 | 编排是固定流程分工；协作是 Agent 之间互相调用/辩论。本项目是编排 + critic 回路 |
| 状态机 | 图的状态是所有节点共享的 TypedDict，节点只增量返回自己产出的字段 |
| generator-critic | 一个生成、一个挑错，critic 的反馈进入下一轮 prompt |
| 工具调用 | Agent 通过工具访问外部事实（如"这条法条真的存在吗"），降低幻觉 |
| 终止条件 | `recursion_limit` + 业务侧 `attempts > max_retry`，双保险 |

**当前已做** ✅：`graph.py` 的图 + review 回边 + 双终止条件；`astream` 节点流直接映射 SSE。

**还要做两件**：

1. **法条存在性校验工具**：生成后抽取所有"第 X 条"，逐条查 Neo4j/语料，不存在的标记为 `unverified`。这是真正意义上的 tool-using Agent，也直接压低幻觉率。
2. **澄清节点**：`identify` 后若领域为 `general` 且问题过短（< 10 字），走 `clarify` 节点反问，而不是硬答。这让图第一次出现"分支而非路由"。

**面试三问**：
- 为什么需要多 Agent？单 Agent 加工具不行吗？→ 行，但职责隔离让 prompt 更短更稳；审查角色需要"挑错"的立场，和"作答"的立场冲突，分开更有效。
- 审查 Agent 会不会误判？→ 会。所以规则审查（可解释、零成本）做基线，LLM 审查做增强，并且**只拦"引用不存在"这种硬错误**，不拦风格问题。
- 怎么防止死循环？→ 图级 `recursion_limit` + 业务级 `attempts` 上限，且重试必须带反馈，否则重试无意义。

## 七、面试题库（12 问，答案要点）

1. **为什么用 GraphRAG 而不是普通 RAG？**
   法律问题有强实体（条号、罪名），向量检索容易召回"语义相似但条号不对"的条文；图能精确约束 + 给出推理路径。并且二跳能发现"同类案例还引用了哪些条"。
2. **双路融合为什么用 RRF 而不是加权分数？**
   向量给的是距离、图给的是命中，量纲不可比；原始实现 `weight * 1/(rank+1)` 会让图路永远排不到第一。RRF 只看名次，无需归一化。
3. **怎么防止 Agent 死循环？**
   图级 `recursion_limit=25` + 业务级 `attempts > max_retry`；且重试必须携带审查反馈，否则是无效重试。
4. **审查 Agent 会不会误判？**
   会。所以只拦硬错误（引用条号不存在、无来源断言），风格问题不拦；规则审查打底，LLM 审查增强，两者结果都记日志便于回溯。
5. **为什么选 FAISS 不用 Milvus / pgvector？**
   单机、无服务依赖、语料万级以内够用；pgvector 的优势在事务一致性，Milvus 在分布式规模，这里都用不上。
6. **只有几百条法条，怎么证明方案有效？**
   gold set + 消融实验证明"检索策略的排序能力"，不是证明"覆盖所有法律"。诚实说明规模限制，并给出扩语料的路径。
7. **二跳查询在 Neo4j 的代价？**
   代价是指数级路径膨胀，靠 `LIMIT` + 关系类型限定 + 只对命中法条做扩展来控制；三跳噪声大于收益，用实验确认。
8. **多轮对话的指代怎么解决？**
   现在是把最近 3 轮拼进 prompt；更好的做法是先做 query rewriting（"那赔偿呢" → 完整问句）再检索。后者是明确的优化项。
9. **幻觉怎么量化？**
   三类指标：引用条号是否存在（可自动）、引用是否在检索结果中（可自动）、断言是否有来源支撑（需人工/LLM 判定）。
10. **为什么不用 LangChain 的 AgentExecutor？**
    本项目流程是确定的（识别→检索→生成→审查），不需要 ReAct 的自由探索；确定流程用图更可控、可观测、可测试。
11. **SSE 并发怎么撑住？**
    所有阻塞调用 `asyncio.to_thread`；SSE 是长连接，单机并发受 worker 数限制，生产要上多 worker + 反向代理。
12. **这套东西上线还缺什么？**
    持久化（对话/案件）、鉴权、限流、索引版本管理、法条时效性更新（法律会修订，这是法律领域特有的坑）。
