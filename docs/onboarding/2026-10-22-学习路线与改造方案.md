# LilMark 项目拆解：学习路线与改造成自己项目的方案

> 本文基于对仓库源码的逐文件核对（Python 1890 行 / 前端 1540 行），
> 结论以代码实际行为为准，不以 README 的宣传描述为准。

---

## 一、先说结论（TL;DR）

**这个项目的价值在于“分层骨架”，不在于工程完成度。**

三句话概括：

1. **真正跑得通的只有一条链路**：`/` 聊天页 → `POST /api/chat` → 领域识别 → 双路检索 → 领域 Agent 生成 → SSE 流式返回。核心代码约 1000 行 Python + 400 行 TS。
2. **一半的 UI 是设计稿**：`/workspace`、`/consultation`、`/evidence`、`/graph`、`/analysis`、`/admin` 六个页面全部读 `frontend/lib/data.ts` 里的硬编码假数据，且它们使用的 CSS 类（`.panel`、`.matter-card`、`.workspace-hero` 等）在 `styles/globals.css` 里**根本没有定义**——打开会基本无样式。
3. **三个宣传亮点没接线**：LangGraph 只有 Streamlit 在用、Reviewer 只有测试在调、`rag.py` 无人调用。

所以学习策略应该是：**读它的架构思路，不读它的“完成度”；改造时保留骨架，自己重写链路和前端。**

### 2.3 一次请求的完整时序（含隐藏的重复调用）

```
浏览器 (/) 
  → fetch /api/chat            [next.config rewrite 代理]
  → FastAPI chat_endpoint
      ├─ identify_domain()      LLM 调用 #1（返回 JSON）
      ├─ hybrid_search()        ← 第 1 次检索
      │    ├─ VectorSearchEngine.query → embedding 调用
      │    └─ graph_search → extract_entities LLM 调用 #2 → Cypher
      ├─ DomainAgent.answer()
      │    └─ hybrid_search()   ← 第 2 次检索（同一问题又跑一遍！）
      │         └─ LLM 调用 #3（生成回答）
      └─ SSE: step(intent) → step(retrieve) → step(generate) → done
```

**注意**：一个问题要花 3 次 LLM 调用 + 2 轮完整检索。`chat.py` 为了拿 `sources_count` 先跑一遍检索，`DomainAgent.answer()` 内部又跑一遍。这是最值得先修的性能问题。

## 三、完成度体检：12 个坑（按严重度）

### 阻断级

1. **前端主视觉是假的**。`/workspace` 系列页面无样式、无接口，`matter-card` 等类在 CSS 中不存在。截图好看是因为另有设计稿，不是这份代码渲染出来的。
2. **Reviewer 未接入**。README 说“审查 Agent 质量校验”，实际 `review_answer()` 只在 `tests/test_reviewer.py` 里被调用。回答里的幻觉检查、免责声明检查全部没生效。
3. **LangGraph 未接入 Web**。`backend/routers/chat.py` 手写了 `identify → search → answer`，完全绕开 `build_agent_graph()`。所谓“多 Agent 工作流”在 Web 端只是一次函数顺序调用。

### 功能级

4. **检索执行两遍**（见上文时序），响应时间直接翻倍。
5. **`graph_search` 的 Cypher 有语法错误**：`build_graph_query()` 里罪名条件拼成 `c.crime CONTAINS "xx"`，但 `MATCH` 只绑定了 `l:Law`，变量 `c` 未定义 → 只要用户问题里带罪名，Neo4j 直接报错。同时实体值用 f-string 拼进 Cypher，**有注入风险**（应改为 `$param` 传参）。
6. **融合打分是伪加权**：`score = weight * 1/(rank+1)`，两路各自从 0.6 和 0.4 起跳，未做分数归一化。结果就是“图检索结果永远排不到第一”，权重参数形同虚设。
7. **FAISS 索引路径是相对路径**：`config.get("embedding_save_path", "data/embeddings")`，settings.yaml 里没这个键 → 落到 `data/embeddings`，相对**当前工作目录**。从 `backend/` 启动和从根目录启动会存到两个地方，然后反复重建索引。
8. **数据量约等于 0**：5 条法条 + 3 个案例。任何真实问题都检索不到东西，回答基本靠模型自己的记忆——这会让你误判“RAG 有没有用”。CAIL 的下载 URL 也已失效。

### 工程级

9. **同步阻塞调用塞进 async 生成器**：`hybrid_search()` 和 `agent.answer()` 都是同步的，在 `event_stream()` 里直接调用会阻塞事件循环。单人演示没问题，两个人同时用就串行。
10. **无持久化**：对话历史只在前端 state，刷新即失；无用户体系；无数据库。
11. **测试是占位测试**：8 个文件共 7~39 行，多数只验证函数能返回，不验证语义。
12. **无 Docker、无日志、无评测集**：说不清“改完到底好没好”，这在答辩/面试里是硬伤。

## 四、学习路线（4 个阶段，按依赖顺序）

原则：**先跑通，再读数据流，再读 Agent，最后读图**。不要从 `coordinator.py` 开始读——它是最抽象的一层，先读会晕。

### 阶段 0：跑起来（半天）

目标不是“功能全”，而是**看到一条完整链路**。

```bash
# 1. 只装 Python 依赖，先不装 Neo4j
uv sync

# 2. 配 key（两个都要，embedding 没 key 连索引都建不了）
export DEEPSEEK_API_KEY=...
export DASHSCOPE_API_KEY=...

# 3. 直接问一句，看它报什么错
uv run python -c "from src.agents.coordinator import ask_agent; print(ask_agent('未签劳动合同怎么维权'))"
```

你会卡在 Neo4j 连不上。这就是第一个学习点：**去 `graph_search.py` 里给 `get_neo4j_driver()` 加 try/except 降级**，让图检索失败时返回空列表，链路仍能跑完。这一步做完，你就理解了“双路检索”里哪一路是可选依赖。

然后起服务：`cd backend && uv run uvicorn main:app --reload` + `cd frontend && npm i && npm run dev`，访问 `/`。

**验收**：浏览器里问一个问题，能看到“意图识别 → 检索 → 生成”三段状态依次点亮。

### 阶段 1：读 RAG 最小闭环（1~2 天）

**读文件顺序（严格按此顺序）**：

```
config.py (29)  →  collector.py (115)  →  vector_search.py (78)
   →  fusion.py (133，先只读 hybrid_search 函数)
   →  domain_agent.py (94)  →  chat.py (44)
```

**要搞懂的 6 个概念**：

| 概念 | 在这个项目里的具体位置 |
|------|------|
| Document + metadata | `build_documents()`：正文进 `page_content`，溯源字段进 `metadata` |
| embedding | `DashScopeEmbeddings`，1024 维，中文场景够用 |
| 向量库 | FAISS 本地索引，`save_local` / `load_local` |
| top_k | `settings.yaml` 的 `vector_top_k: 5` → `final_top_k: 8` |
| prompt 拼装 | `domain_agent.py` 第 48~67 行，`[1] xxx` 编号注入 |
| 溯源 | metadata 反查 `law_name + article_number` → 前端 sources 列表 |

**动手验证（很重要，别只读）**：

1. 把 `vector_top_k` 改成 1 和 20，同一个问题对比回答差异 → 理解召回与噪声。
2. 在 `domain_agent.answer()` 里 `print(context_text)` → 亲眼看模型到底拿到了什么。**90% 的 RAG 效果问题都能在这一步暴露。**
3. 问一个内置数据里没有的问题（比如“公司不给加班费”），观察它是否硬编法条 → 理解“检索不到时模型会瞎编”。

**验收**：你能不看代码画出“问题 → 向量化 → 召回 → 拼 prompt → 生成 → 溯源”这条线。

### 阶段 2：看清“多 Agent”到底多在哪（2~3 天）

**读**：`coordinator.py`（重点 `identify_domain` + `build_agent_graph`）→ 5 份 `src/agents/config/*.yaml` → `reviewer.py`

**必须建立的清醒认知**：

- 这里的 multi-agent = **一次 LLM 分类 + 5 份不同的 system prompt**。领域 Agent 之间没有通信、没有协商、没有工具调用。
- LangGraph 图是**线性**的：`identify_intent → 某个 domain → END`。没有环、没有反思、没有重试。用 LangGraph 属于“杀鸡用牛刀”，换成 if/else 完全等价。
- `reviewer.py` 是正则校验，不是 LLM 审查，而且没接线。

**这就是你最容易做出“增量”的地方**——把它变成真的多 Agent：

1. 加**澄清节点**：`identify_intent` 后判断置信度低 → 走 `clarify` 节点反问用户（条件边，第一个真正的图能力）。
2. 加**审查回路**：`generate → review → (不通过) → 带问题清单重新 generate`（`add_conditional_edges` 回到生成节点）。这是 LangGraph 相对 if/else 的唯一实质优势，也是答辩最好讲的一点。
3. 加**法条校验工具**：让 Agent 调用 `lookup_article()` 查证引用是否真实存在，而不是靠正则。

**验收**：你能说清“为什么这里需要图，而不是三个函数调用”。

### 阶段 3：读懂 GraphRAG（2~3 天）

**读**：`kg_builder.py`（151）→ `graph_search.py`（157）→ 回头看 `fusion.py`

**概念对应**：

| 概念 | 代码位置 |
|------|---------|
| 图 schema | `(:Law {law_name, article_number, chapter, content})`、`(:Case {case_id, crime, fact, judgment})` |
| 关系 | `(:Case)-[:APPLIES]->(:Law)` |
| MERGE 幂等 | `build_cypher_for_law_node()`，重复导入不产生重复节点 |
| 实体抽取 | `extract_entities()`：条款号 / 罪名 / 法律术语，三类 |
| 多跳 | `build_graph_query(hop=2)`：法条 → 案例 → 另一法条 |
| 融合 | 加权 + `_is_duplicate()` 去重 |

**动手验证**：在 Neo4j Browser（`localhost:7474`）里手写这三条，比读代码有效 10 倍：

```cypher
MATCH (l:Law) RETURN l LIMIT 10;
MATCH (c:Case)-[:APPLIES]->(l:Law) RETURN c.case_id, l.article_number;
MATCH (l:Law {article_number:'第八十二条'})-[r]-(x) RETURN l, r, x;
```

**验收**：你能说清“一条法条是怎么通过案例连到另一条法条的”，以及为什么这比纯向量检索强（结构化约束、可解释路径）。

### 阶段 4：前后端契约（1 天）

**读**：`backend/services/streamer.py`（13 行）→ `backend/routers/chat.py` → `frontend/lib/api.ts` → `frontend/components/chat/ChatContainer.tsx`

**重点**：`parseSSEStream` 是手写的 SSE 解析（按行切 `event:` / `data:`，处理半包 buffer）。这是本项目前端最有含金量的 80 行，读懂它你就掌握了流式 UI 的核心。

**验收**：你能解释“为什么 `buffer = lines.pop()` 不能省”。

> 时间不够的话：阶段 2 的“审查回路”和阶段 3 的 Neo4j 手写查询是**最低必做项**，其余可跳。

## 五、改成“你的项目”的方案

### 5.1 先明确一件事

这个仓库最值钱的是**领域无关的骨架**：分层 + 配置驱动 + 引用溯源 + 流式交互。
改造的核心动作不是“改代码”，而是**换领域知识、换数据、加一个别人没有的亮点**。
只改名字和配色 = 一眼假，答辩第一个问题就会问穿。

### 5.2 三条路线，按你的目标选

#### 方案 A（推荐）：换领域，保留骨架 — 约 3 周

适合：毕设 / 求职作品集 / 想讲清 RAG 的人。

| 步骤 | 具体动作 | 占比 |
|---|---|---|
| 1. 选题 | 选一个**你能拿到数据**的垂直领域，别选“通用助手” | 1 天 |
| 2. 数据 | 采集 → 清洗 → 结构化 → 建索引/建图 | **60% 工作量** |
| 3. 领域配置 | 5 份法律 YAML → 你的 3~4 份领域 YAML | 1 天 |
| 4. 检索改造 | 换实体 schema、Cypher 参数化、调融合权重 | 2 天 |
| 5. 前端 | 只保留 `/` 聊天页，加一个“证据/来源”侧栏；放弃 workspace 壳 | 3 天 |
| 6. 亮点 | 从下面选 1~2 个做深 | 5 天 |
| 7. 收尾 | 评测集 + 指标 + 部署 + 重写 README | 3 天 |

**候选领域（按数据可得性排序）**：

| 领域 | 数据源 | 难点 |
|---|---|---|
| 医疗指南问答 | 临床指南 PDF、药品说明书 | 需 OCR，术语多 |
| 财税/政策补贴 | 税务总局公告、地方政策 | 时效性强，要版本管理 |
| 企业内部制度助手 | 公司员工手册、SOP（可自己造） | 数据干净但无公开数据集，说服力弱 |
| 学术论文助手 | arXiv API | 英文为主，门槛低但同质化严重 |
| 保险条款解读 | 保险条款库 | 条款结构化程度高，很适合图谱 |

**亮点清单（选 1~2 个，不要贪多）**：

1. **原文高亮**：sources 从字符串升级为 `{doc_id, char_start, char_end}`，点击引用跳转并高亮原文段落。视觉冲击最强，业界也在做。
2. **审查回路 + 置信度**：Reviewer 真正接入，不通过则带问题清单重生成，前端展示“第 2 轮修正”。最能讲清 Agent 编排。
3. **查询改写**：多轮对话时把“那赔偿呢”改写成完整问题再检索（解决指代消解），效果提升明显、代码量小。
4. **评测看板**：50 条人工标注问题 + 命中率/引用准确率/幻觉率三条指标，改前后对比。**最能证明你工程能力的一项**。

#### 方案 B：不改领域，专做工程加固 — 约 2 周

适合：想突出后端/架构能力。把第三章 12 个坑逐个填：

```
异步化（retrieval 用 asyncio.to_thread 或改 async client）
→ Cypher 参数化 + 修 graph_search 的 c 变量 bug
→ 检索只跑一次，sources 从 DomainAgent 内部返回
→ Reviewer 接入 + 重试回路
→ 补 30 条真实法条 + 20 个案例，修 CAIL 下载
→ pytest 从占位测试改成行为测试
→ Docker Compose（neo4j + api + web）
→ 评测集 + 指标
```

交付物是一份“我修了什么、为什么、效果提升多少”的报告。这个叙事在面试里非常吃香。

#### 方案 C：只做前端 — 约 5 天

适合：前端方向。砍掉 Python 后端，Next.js 直接调 LLM API，重点做交互（流式打字机、引用卡片、图谱可视化）。`lib/api.ts` 可以直接复用。

### 5.3 改造里程碑（按 A 方案，3 周）

| 周 | 目标 | 验收标准 |
|---|---|---|
| W1 | 跑通 + 定题 + 数据管线 | 能回答 20 个你领域内的问题，且引用来自**你自己的数据** |
| W2 | 领域配置 + 检索改造 + 评测集 | 50 条评测集跑通，命中率基线数字写在 README 里 |
| W3 | 前端重做 + 亮点 + 部署 + 文档 | 一个陌生人不看你的讲解能用起来 |

### 5.4 必须重写、不能只改名的东西

- **`README.md`**：现在写的是别人的成果和技术栈。你要写“我的问题定义 / 我的数据 / 我的评测数字 / 我的增量”。
- **`docs/superpowers/`**：4935 行实施计划，是原作者的过程文档。留着会显得像照抄，建议删除或移到 `docs/original/`。
- **Git 历史**：建议新建仓库，首次提交写清 `Initial import based on Lexiora (MIT)`。
- **法律领域的 5 份 YAML**：换成你的领域，`DOMAIN_MAP` 关键词表也要换（现在全是“劳动合同/盗窃/行政处罚”）。
- **`frontend/lib/data.ts`**：171 行假数据必须删掉或替换成真接口。

### 5.5 合规：这不是可选项

Lexiora 是 **MIT 协议**。允许修改、商用、闭源分发，但**必须保留原版权声明和 LICENSE 文件**。

- 保留 `LICENSE`，README 里加一句“本项目基于 qscoder23/lexiora 二次开发”。
- 如果是毕设/论文：必须在文档里明确区分“原有部分”和“我的增量”，否则构成学术不端。评审最常查的就是这个。
- 别把原作者的设计文档当成自己的设计文档提交。
