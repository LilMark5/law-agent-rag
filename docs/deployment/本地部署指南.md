**检索质量（33 条 gold，法名 + 条号粒度，`Recall@5` / `MRR`）**

| 配置 | Recall@5 | MRR | 单查询耗时 |
|---|---|---|---|
| 字符二元组兜底（改造前） | 0.545 | 0.336 | 102 ms |
| BM25 单路 | 0.727 | 0.482 | 23 ms |
| 向量单路 | 0.848 | 0.733 | 404 ms |
| 等权 RRF（浅召回 5/8） | 0.818 | 0.692 | 237 ms |
| **加权 RRF（深召回 20/20）** | **0.879** | **0.741** | 449 ms |

两个反直觉结论，都写进了 `config/settings.yaml` 的注释：

1. **等权融合会低于单路最优**（0.818 < 0.848）。弱通道的"噪声提名"和强通道的有效提名等权累加，反而把正确答案挤下去。降权到 `vector 1.0 / bm25 0.2` 才有增益。
2. **必须先深召回再截断**。每路只取 5 条就融合，两路结果几乎重合，融合等于白做；改成各取 20 条后 Recall 从 0.848 升到 0.879。

复现命令：

```bash
uv run python scripts/eval_retrieval.py --mode vector --top-k 5
uv run python scripts/eval_retrieval.py --mode hybrid --top-k 5
uv run python scripts/eval_retrieval.py --mode hybrid --no-graph   # 消融：看图检索贡献
uv run python scripts/sweep_fusion.py --depth 20    # 权重扫描
```

### 这一轮修掉的三个"看起来能跑、其实在扣分"的问题

| 症状 | 真实原因 | 代价 | 处理 |
|---|---|---|---|
| 每条查询检索都要 5 秒 | 每次请求都 `VectorSearchEngine()`，构造客户端 + 反序列化 FAISS 约 5s | 首问与每问都慢 | `get_engine()` 按索引路径缓存；`backend/main.py` 加 lifespan 预热 |
| 图检索拖低结果 | `l.content CONTAINS 术语` 召回无排序的任意法条，等于把 BM25 重做一遍还更差 | MRR 0.741→0.644，延迟 +4.8s | 只按条号精确匹配；`graph_use_llm_entities: false` 关掉检索链路上的 LLM 抽取 |
| 审查把正确回答打回重写 | 模型写「第10条」，语料存「第十条」，存在性校验判成"编造" | 每题多一次生成，+8s | `reviewer.normalize_article()` 归一化阿拉伯数字 |

> 另外：「刑法第232条」这类阿拉伯数字条号，正则原本匹配不到（语料是中文数字）。
> 现在 `extract_article_numbers()` 会做 `232 → 二百三十二` 的转换，并用**真实法名词典**
> 识别"刑法"以收窄跨法重名的条号（第232条在民法典、刑法、民诉法里都有）。

## 2. 一次性安装（4 条命令）

```bash
uv sync                                   # 1. Python 依赖，自动建 .venv + 装 Python 3.11
cd frontend && npm install && cd ..       # 2. 前端依赖
cp .env.example .env                      # 3. 配置模板 → 实际配置（然后填 Key）
docker compose up -d                      # 4. Neo4j
```

`uv sync` 会读 `uv.lock`，装的是锁定版本，不会因为上游发版而随机坏掉。

## 3. 配置 `.env`

打开项目根目录的 `.env`（已被 `.gitignore` 忽略）：

```ini
DEEPSEEK_API_KEY=sk-xxxxxxxx        # 必需，https://platform.deepseek.com/api_keys
DASHSCOPE_API_KEY=sk-xxxxxxxx       # 可选，https://bailian.console.aliyun.com/
NEO4J_PASSWORD=law_agent_rag_2026     # 必须与 docker-compose.yml 用的密码一致
```

**优先级：`.env` > 系统环境变量 > `config/settings.yaml`。**

> **为什么 `.env` 放在最前**：这是踩过的坑。最初用的是 `os.environ.setdefault`（系统变量优先），
> 结果系统里残留一个旧的、已失效的 `DASHSCOPE_API_KEY`，会**静默覆盖** `.env` 里新填的 Key，
> 表现为“我明明填了新 Key，却一直报 401”。现在 `.env` 为准，并在两者不一致时打印一行警告：
>
> ```
> 环境变量 DASHSCOPE_API_KEY 与 .env 不一致（系统=sk-****(len=35) / .env=sk-****(len=116)），以 .env 为准
> ```
>
> 看到这行就说明：你机器上有个更早设置的变量，建议去「系统属性 → 环境变量」里删掉，或重启终端让 `.env` 干净生效。

`.env` 的解析是在 `src/config.py` 里手写的（约 20 行），没有引入 `python-dotenv`。
空值（`KEY=`）不会覆盖已存在的系统变量，因此“注释掉某个 Key”会退回系统变量而不是变成空串。

关于 `NEO4J_PASSWORD`：`docker-compose.yml` 里写的是

```yaml
NEO4J_AUTH: neo4j/${NEO4J_PASSWORD:-law_agent_rag_2026}
```

Docker Compose 会自动读取同目录的 `.env`。**改密码要两处同步**，否则后端会 `AuthError`。

> 如果容器已经用旧密码初始化过，改 `.env` 不会生效——Neo4j 只在数据目录为空时读 `NEO4J_AUTH`。
> 需要 `docker compose down -v` 清空数据卷后重新启动（会丢图谱，重新导入即可）。

### Embedding Key 从哪来（可选，不填也能跑）

项目默认用阿里云百炼的 `text-embedding-v3`。

1. 打开 https://bailian.console.aliyun.com/ ，用支付宝/淘宝登录，完成**个人实名认证**（否则建不了 Key）
2. 首次进入会弹服务协议，点「确认开通，并领取免费额度」
3. 控制台右上角**设置** → 左侧「**API-KEY**」→「创建 API Key」（归属账号选主账号，业务空间选默认）
4. 复制 `sk-` 开头的字符串，填进 `.env` 的 `DASHSCOPE_API_KEY=`
5. 验证：`uv run python scripts/doctor.py --check-api`，看到 `[OK] Embedding 调用：维度 1024` 即成功

免费额度：每个模型 100 万 token / 90 天（华北2 北京地域）。本项目 3942 条法条约 30~40 万 token，一次建索引够用。

**401 的两个常见原因**

- Key 不是百炼的：阿里云 `AccessKey ID/Secret` 不能当百炼 API Key 用，必须是「API-KEY」页面创建的 `sk-` 串
- **地域不匹配**：百炼不同地域的 Key 和域名完全隔离。本项目的 `base_url` 是 `dashscope.aliyuncs.com`（北京），国际版 Key 必须配 `dashscope-intl.aliyuncs.com`，否则一律 401

**完全免费的替代：硅基流动**

如果不想做阿里云实名，可用 [硅基流动](https://cloud.siliconflow.cn/me/account/ak) 的 `BAAI/bge-m3`（1024 维，长期免费）。
项目已把 Embedding 层抽象成 **任意 OpenAI 兼容服务**，换厂商只改 `config/settings.yaml`：

```yaml
embedding:
  base_url: "https://api.siliconflow.cn/v1"
  model: "BAAI/bge-m3"
  dimension: 1024          # bge-m3 是 1024 维；换模型注意同步改
  api_key: ""              # 走 .env 的 DASHSCOPE_API_KEY，或改成一个专用变量名
```

同理也支持 OpenAI `text-embedding-3-small`、智谱、Moonshot 等任何兼容 `/embeddings` 的服务。**换 provider 后必须加 `--force` 重建索引**，因为不同模型的向量空间不可混用。

> **不能只用 DeepSeek 的 Key**：DeepSeek 官方 API 只有对话模型，没有 `/embeddings` 接口
> （实测 `POST https://api.deepseek.com/embeddings` 返回 404，`/models` 列表里也只有 `deepseek-chat` / `deepseek-v4-pro`）。
> 所以向量检索必须另找一家 Embedding 服务。

**分批与并发**：`text-embedding-v3` 单批上限 10 条，一次塞 3942 条会被拒。`src/retrieval/embedding.py` 显式分批（默认 10 条/批、4 线程并发、指数退避重试），实测 3942 条约 3~5 分钟。若遇到 429 限流，把 `embedding.concurrency` 调到 1~2。

**不填会怎样**：`hybrid_search` 自动跳过向量路，用 BM25 + 图谱融合。功能不受影响，只是“拖欠工资→未及时足额支付劳动报酬”这类近义改写召回不到。

## 4. 初始化数据

三个脚本职责不同，按需执行：

```bash
# ① 法条 → Neo4j（必需，约 10 秒）
uv run python scripts/import_sample_data.py

# ② 构建 FAISS 向量索引（可选，需要有效 Embedding Key，1~5 分钟）
uv run python scripts/build_index.py

# ③ 重新抓取法条语料（可选，仅当你想更新语料）
uv run python scripts/fetch_laws.py --all
```

`data/processed/laws.json` 已经在本机生成好了（3.4 MB），**不跑 ③ 也能直接用**。

**为什么建索引要单独跑？** 原来 `hybrid_search` 用的是 `load_or_build`，索引不存在时会在**用户请求线程里**给 3942 条法条现场算 Embedding，首屏要等几分钟，还会烧额度。我改成了「只加载、不构建」，构建走 `scripts/build_index.py`。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `[Errno 10048] address already in use` | 上一次的 uvicorn 没退干净，`--reload` 会留子进程 | `Get-NetTCPConnection -LocalPort 8000` 找到 PID 后 `Stop-Process -Id <PID> -Force` |
| 改代码后行为没变 | 同上，旧进程还占着端口，新进程根本没起来 | 同上，确认端口释放后再启动 |
| `AuthError: The client is unauthorized` | `NEO4J_PASSWORD` 与容器密码不一致 | 改 `.env` 后 `docker compose down -v && docker compose up -d`，再重新导入 |
| `401 Incorrect API key provided` | Embedding Key 失效 | 换 Key；或先不管，检索会自动走 BM25 |
| **填了新 Key 但一直 401** | 系统环境变量里有旧的同名变量，静默覆盖 `.env` | 已在 `src/config.py` 改为 `.env` 优先；启动时会打印"系统=... / .env=...，以 .env 为准"。确认打印的是新 Key 后仍报错，才是 Key 本身问题 |
| `curl` 访问外部接口报 `HTTP 000` / `CRYPT_E_REVOCATION_OFFLINE` | Windows 下 curl 走 schannel，吊销服务器不可达；或本机代理挂了（`127.0.0.1:4810`） | 不是项目问题。加 `--ssl-no-revoke`，或改用 Python 验证（`urllib`/`openai` 不查 CRL）。代理变量在 `env | grep -i proxy` 里查 |
| `Authentication Fails (governor)` | DeepSeek Key 缺失/无效 | 填 `DEEPSEEK_API_KEY` |
| 生成成功但 answer 为空、审查报“未包含法条引用” | 推理模型（`deepseek-v4-pro`）先消耗思考 token，`max_tokens` 不够，`content` 为空 | 已内置检测并抛出明确错误；把 `llm.max_tokens` 调到 4096+，或改用 `deepseek-chat` |
| 首问特别慢（5 秒+） | 历史 bug：缺索引时同步建索引、无 Key 仍发请求 | 已修；若仍慢，看后端日志的 `向量检索不可用` / `图检索不可用` |
| `/workspace` 等页面样式全丢 | 这些页面用的 CSS 类在 `globals.css` 里没定义，且读的是假数据 | 属于未完成功能，不是部署问题 |
| `npm install` 提示 next@15.1.0 有 CVE | 锁定的版本偏旧 | 后续可升到 15.x 最新补丁版，见第 8 节 |

## 8. 往生产再走一步（可选）

本地跑通之后再考虑这些，现在不用做。

**前端**

```bash
cd frontend
npm run build && npm run start   # 默认 3000
```

`next build` 会做类型检查，能提前发现页面级错误。另外建议把 `next` 升到 15.x 最新补丁版（当前 15.1.0 有已披露漏洞）：

```bash
npm install next@15
```

**后端**

```bash
uv run uvicorn backend.main:app --host 0.0.0.0 --port 8000 --workers 2
```

注意 `--reload` 只能用于开发；生产别开。多 worker 时 BM25 索引会每个进程各建一份（3942 条约 0.3 秒、几十 MB），可以接受。

**待办（部署相关）**

- Key 不要写进 `config/settings.yaml`，走环境变量
- `data/raw`、`data/processed` 共约 4 MB，是否入库自己定；建议入库以便复现
- 项目目前**不是 git 仓库**，写简历前先 `git init` 并做首次提交
